Getting started with Sprint Ledger

Private beta guide · updated 12 September 2026

Sprint Ledger reconstructs the membership history of every sprint your site has ever run, keeps it current from Jira's own events, and gives you the answer as JQL functions and as issue fields you can put in a column. This page is everything a beta site needs: install, what the first few hours look like, the queries, and how to check the numbers against Jira's Sprint Report.

1. Install

Your install link is in the invitation email. Open it while signed in to Jira, pick the site, review the permissions and install. It takes about a minute and needs a Jira administrator; there is nothing to configure afterwards.

Sprint Ledger is a Forge app: it runs inside Atlassian's infrastructure, and no issue data leaves your Jira. The consent screen asks to read Jira work, sprints, boards and projects, to write Jira work (used only to fill its own eight read-only fields) and to use Forge app storage.

Installing starts the reconstruction by itself. You do not need to pick projects: every project that has a scrum or team-managed board is tracked by default, and you can turn projects off on the admin page at any time.

2. The first reconstruction

The app reads the changelog of every issue that has ever been in a sprint and rebuilds, sprint by sprint, who was in it at the start, what arrived later, what left, what was finished and what rolled over.

Watch it at Jira settings → Apps → Sprint Ledger. The page shows a progress banner with an estimate (it appears once the run is about 5% in, because the first stages are dominated by scheduling), and a table of every board it has discovered with its sprint count and state, plus a Re-run button per board and Rebuild every tracked board.

How long it takes

A full reconstruction costs about two Jira API points per issue that has ever been in a sprint, and the app spends at most 12,000 points an hour so that it never crowds out your other apps or your own integrations. That works out at roughly 6,000 issues an hour.

Issues that have ever been in a sprintExpect
under 2,000a few minutes
10,000about 2 hours
30,000about 5 hours
100,000about 17 hours

It is safe to walk away. The run checkpoints itself after every batch, pauses when the hourly budget runs low, resumes on its own, and survives you closing the page. A rebuild is also safe to start at any time: the ledger is rewritten in place, never duplicated.

The fields and the JQL functions start answering when the run reaches its last stage, so treat the admin page saying the run has finished as the moment to start querying. From then on the ledger is kept current live: a drag into or out of a sprint shows up in the fields within a few seconds, a sprint start or completion within about five, and an hourly pass reconciles anything an event missed.

3. Two things to check first

Both are one-time Jira configuration, and both are the usual reason a beta site thinks something is missing.

Share each board's filter with the project

Jira shows a board to an app only when the app can see the board's filter. A board with a private filter is invisible, and its sprints will be missing from the ledger. If a board you expected is not in the admin page's table, open Filters → the board's filter → Details → Edit permissions, share it with the project (or with everyone logged in), and then press Rebuild every tracked board.

Add the fields to team-managed projects

The fields work as columns and in JQL everywhere with no setup at all. They only need adding if you want to see them on the issue view:

  • Team-managed project: Project settings → Fields → Add field, pick the fields whose name ends in "(Ledger)", and drag each one into the layout of every work type that should show it.
  • Company-managed project: add the fields to the issue screen the project uses, as you would any other custom field.

4. The eight fields

All eight are read-only and written only by the app, in bulk, without touching issue history. Five of them describe the issue's latest sprint, meaning the most recent started sprint the issue counts in, including one it was removed from.

FieldTypeWhat it holds
Sprint scope (Ledger)textHow the issue entered its latest sprint: Committed, Added after start, Removed, or Added then removed
Added to sprint (Ledger)date and timeWhen the issue entered its latest sprint
Removed from sprint (Ledger)date and timeWhen it left; empty unless it was removed
Sprint start (Ledger)date and timeStart date of the latest sprint
Sprint end (Ledger)date and timePlanned end date, or the completion date once the sprint is closed
Sprints carried (Ledger)numberHow many closed sprints the issue left unfinished
Original sprint (Ledger)textName of the first sprint the issue was ever in
Sprint ledger tagstext listOne token per sprint: c: committed, a: added after start, r: removed, d: completed, x: carried over, each followed by the sprint ID. This is what the JQL functions search; the newest 100 sprints are kept per issue

They sort, they filter and they export like any other field:

"Sprint start (Ledger)" >= 2026-07-01 AND "Sprint scope (Ledger)" = "Added after start"
project = ACME AND "Sprints carried (Ledger)" >= 3 ORDER BY "Sprints carried (Ledger)" DESC
"Removed from sprint (Ledger)" >= -14d

5. The six JQL functions

Each one is used as issue in f(...) or issue not in f(...), and works wherever JQL works: filters, boards, dashboards, automation rules and filter subscriptions.

FunctionReturns
addedAfterSprintStart(sprint?, board?)Issues that joined the sprint after it started
removedFromSprint(sprint?, board?)Issues taken out after it started and before it closed
committedTo(sprint?, board?)Issues that were in the sprint the moment it started
completedIn(sprint?, board?)Issues in the sprint at completion whose status counted as done
carriedOverFrom(sprint?, board?)Issues in the sprint at completion that were not done
carriedOver(n)Issues that have rolled out of at least n closed sprints

The sprint argument is a sprint name, a numeric sprint ID, or nothing at all, which means every active sprint on the site. A name matches every sprint with that name on any board, which is usually what you want across parallel boards; add the board name as a second argument to narrow it, or use the ID. A name that matches nothing gives you a message in the JQL editor rather than a silent empty result.

project = ACME AND issue in addedAfterSprintStart("ACME Sprint 42")
sprint in openSprints() AND issue in addedAfterSprintStart()
issue in committedTo("ACME Sprint 41") AND issue not in completedIn("ACME Sprint 41")
issue in removedFromSprint("ACME Sprint 41") AND issue not in committedTo("ACME Sprint 42")
issue in carriedOver(2) AND statusCategory != Done ORDER BY "Sprints carried (Ledger)" DESC
issue in addedAfterSprintStart("Sprint 7", "ACME board")

The fourth one is the query people write to us about most: what was dropped from last sprint and never picked back up.

6. What is not there yet

You are early, so here is the honest list. Everything below is built during the beta and arrives by app update, with no action from you:

  • The dashboard gadget (committed, added, removed, completed, carried, say/do and scope change per sprint, with a chart).
  • CSV export per sprint and per board, including who added or removed each issue and when.
  • The settings on the admin page: the definition of "done", whether subtasks count, and how far back the deep scan reaches. Until then the defaults are in force: done means the board's rightmost column, subtasks are tracked but left out of counts and tags, and the sweep for issues that were removed from every sprint covers the last 12 months.
  • The project settings page, for teams that should see their own project without a Jira admin.

What is already there and safe to lean on: the reconstruction, the live capture, the hourly reconciliation, the eight fields and the six functions.

7. Checking the numbers against the Sprint Report

This is the one thing we would like every beta site to do, and it takes about fifteen minutes. Pick three closed sprints, ideally ones you remember, and compare.

  1. Open the board, Reports → Sprint Report, and choose the sprint.
  2. Run the four queries below with that sprint's name and compare each list with the report's: "Completed Issues", "Issues Not Completed", "Issues Removed From Sprint", and the asterisked issues (the report's footnote marks those as added after start).
issue in committedTo("ACME Sprint 41")
issue in addedAfterSprintStart("ACME Sprint 41")
issue in removedFromSprint("ACME Sprint 41")
issue in completedIn("ACME Sprint 41")
issue in carriedOverFrom("ACME Sprint 41")

Three differences are expected and are not bugs:

You will seeWhy
Subtasks are missing from bothJira's report excludes them and so do we, by default. The ledger still tracks them, and a setting to count them is coming.
An issue that was added after the start and then removed again appears in both addedAfterSprintStart and removedFromSprint, while Jira's report lists it only under "Issues Removed From Sprint"Both statements are true, and reporting on scope change needs both. Jira shows each issue once, in one list.
An old sprint disagrees about what counts as completed"Completed" means the issue's status was in the board's rightmost column. If the board's columns were rearranged since that sprint closed, the current mapping is used. A setting to define done by status category instead is coming.

An issue that was committed, removed and then put back counts as committed, exactly as Jira's report treats it. Anything else that differs is a bug and we want to hear about it: the sprint, the issue key and what each side said is enough.

8. Privacy, data and uninstalling

Sprint Ledger stores issue IDs and keys, project IDs, sprint and board metadata, timestamps, the account ID of whoever added or removed an issue, and the values it computes. It does not store summaries, descriptions, comments or attachments. Nothing is sent anywhere: there are no external services and no egress, because the app runs on Atlassian's own infrastructure and its data lives in Forge storage attached to your installation, which also means it inherits your site's data residency.

Account IDs are captured so that an export can say who changed the scope; a setting to turn that off is part of the settings work above, and until it ships we will turn it off for you on request. Uninstalling the app removes the installation and the storage that belongs to it; an explicit "Delete all ledger data" button arrives on the admin page with the rest of the settings.

The beta is free. When the app is listed, beta sites keep it free for 60 days from the listing date, and sites with up to 10 users stay free after that.
