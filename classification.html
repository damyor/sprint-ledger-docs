How Sprint Ledger counts

Definitions and deviations · updated 17 September 2026 (app version 2.9.0)

Every answer Sprint Ledger gives, in the JQL functions, the fields, the gadget and the export, comes from one reconstruction of each sprint, built from the history Jira keeps for every issue. This page says exactly how that reconstruction decides what an issue did in a sprint, so that a number can be checked, and where it differs from Jira's own Sprint Report.

What it reads

For each issue: every change Jira recorded to its Sprint field, status and estimate, and when the issue was created. For each sprint: its start date, its completion date, its state and the board it was created on. For each board: which statuses sit in which column, and which field holds the estimate. Nothing is guessed from the issue's current state when the history says otherwise.

From the Sprint field's history the app builds each issue's membership of each sprint: periods that begin when the sprint was added to the issue and end when it was taken away. An issue created directly inside a sprint has no such change in its history, so its membership begins when the issue was created.

The definitions

Two moments decide everything: the sprint's start, its start date, and its close, its completion date, or now for the active sprint.

Completed outside is Jira's own rule. An issue that was already done when the sprint started, and still done when it closed, did no work in that sprint, so Jira's report lists it apart and counts it neither as completed nor as not completed. Sprint Ledger does the same: such an issue is in neither completedIn() nor carriedOverFrom(), it does not count in say/do, and its tag is o:, so "Sprint tags (Ledger)" = "o:5231" finds the ones of sprint 5231. The commonest case is an issue carried over and finished between two sprints. An issue that was reopened during the sprint and done again, or that became done after the start while it was out of the sprint, is completed, as in the report.

Done means, by default, a status in the rightmost column of the sprint's board, as the Sprint Report counts it. An administrator can switch to "any status in the Done category" on the admin page; the whole history is then classified again, without reading Jira.

Completed, carried over and completed outside are final only for closed sprints. For the active sprint they describe the state now and change until it closes, which is why completedIn() and carriedOverFrom() answer for closed sprints only.

Estimates. A committed issue's estimate is the one it had at the start, an added issue's the one it had when it joined, as the Sprint Report does; the completed estimate is the one at the close, or at the moment of removal for a removed issue. When the estimate was never changed, its current value is used.

How the numbers compare with the Sprint Report

Five differences are expected, and none is a bug:

You will seeWhy
Subtasks missing from bothJira's report leaves them out and so does Sprint Ledger by default. The admin page's subtask setting counts them.
An issue added after the start and then removed appears in both addedAfterSprintStart and removedFromSprint, while the report lists it only under "Issues Removed From Sprint"Both statements are true, and a scope-change report needs both. The report shows each issue once, in one list.
An old sprint's completed count differs"Completed" follows the board's columns as they are now. If the columns were rearranged after the sprint closed, the count can move. Defining done by status category on the admin page makes the answer independent of the columns.
An issue that was in the sprint but no longer matches the board's filter is counted by Sprint Ledger and missing from the reportJira's report shows only the sprint's issues that the board's filter matches at the moment you open it, so it changes whenever the filter or the issue changes. Sprint Ledger counts every issue that was in the sprint, as JQL's sprint = … does, so a sprint's history stays as it was. The admin page's check asks Jira whether the filter still matches and names these issues.
On a site where only some projects are turned on, an issue of a project that is off is listed by the report and missing from Sprint LedgerSprint Ledger reads no issue of a project it is turned off for. With "Every project with a sprint board" on, it counts every issue on a tracked board's sprints, including issues of projects that have no board of their own.

On the app's test site, fifty closed sprints were compared list by list with Jira's Sprint Report, ten of them built to exercise the cases above and forty sampled from five years of a larger project: forty-nine agreed exactly, and the fiftieth differed only by the second case in the table.

Checking a sprint yourself

The quickest check is on the admin page: Compare with Jira's Sprint Report reads Jira's own report for the last three closed sprints of a board and compares it with the ledger issue by issue, including each issue's estimate at the start and at the close, and names every difference with its reason. To check a sprint by hand:

  1. Open the board, Reports → Sprint Report, and choose a closed sprint.
  2. Run these with the sprint's name, and compare each list with the report's "Completed Issues", "Issues Not Completed", "Issues Removed From Sprint" and the asterisked issues; "Issues completed outside of this sprint" is "Sprint tags (Ledger)" = "o:" followed by the sprint's ID:
issue in committedTo("ACME Sprint 41")
issue in addedAfterSprintStart("ACME Sprint 41")
issue in removedFromSprint("ACME Sprint 41")
issue in completedIn("ACME Sprint 41")
issue in carriedOverFrom("ACME Sprint 41")

For an issue that appears in one list and not the other, open it and add the Sprint history (Ledger) panel: it shows when the issue entered and left the sprint and the status it had at the close, which is usually the whole explanation.

Anything that differs other than the five cases above is a bug, and we want to hear about it: the sprint, the issue key and what each side said is enough (Support).
